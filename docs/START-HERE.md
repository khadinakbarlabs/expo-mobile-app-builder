# Start where your app is

You can begin with an idea, a research question or a working app. Tell the assistant what you want to achieve in ordinary language. It should choose the relevant roles and workflows for you; you do not need to learn the department names or install every skill separately.

## I have an idea or want to research an opportunity

Say:

> I want to build an app for [audience] that helps with [problem]. Start by researching the opportunity before choosing features. My target market is [country/language].

The assistant first checks what you already know and any available project files. It researches demand, Apple/Google Play competitors, review themes and useful design patterns, using public sources or a bounded Apify plan. You receive a concise evidence brief, uncertainties and a proposed first useful feature. No paid Actor runs start without sufficient existing budget authorization.

Then you can choose the next useful step: validate the idea, refine positioning, design the core journey or build a small working slice. The assistant uses iOS and Android by default when the platform is unspecified, labels that assumption, and checks it before platform-specific work or account setup. It records the product decisions so later stages reuse them.

## I already have an app

Say:

> Inspect this app and help me [fix a problem / improve the design / add a feature / prepare a release / grow it]. Preserve the current product direction and working features.

The assistant starts with the repository instructions, current stack/version, working changes and relevant evidence. It identifies what is already implemented and asks only for information that changes the next action. It doesn't scaffold a replacement app or begin a full market study automatically.

For a reported bug, it reproduces the affected interaction where tools permit, makes a focused fix and verifies the behavior. For design work, it reviews the actual flow and preserves established choices unless you ask for a redesign. For launch work, it checks the intended build, store assets and release evidence. For growth, it begins with your current audience, listing, website, creators, ads and available analytics; recommendations distinguish observed results from estimates.

Existing apps can use any relevant framework. Expo instructions apply when the app actually uses Expo; native iOS, Android, Flutter or another stack needs its own appropriate tools and documentation. The assistant names framework coverage gaps before applying incompatible commands or proposing a migration.

## I only need one result

| Your request | What you receive |
| --- | --- |
| Research a niche or competitors | Dated evidence, review themes, opportunities and unknowns |
| Improve onboarding or a paywall | Flow review, screen/error states, design changes and acceptance checks |
| Fix a bug or add a feature | Focused repository change and affected-behavior verification |
| Analyze Apple App Store and Google Play | Store comparison, ASO opportunities and listing experiments |
| Find TikTok, Instagram or YouTube creators | Source-linked shortlist, fit rationale and campaign pilot |
| Research TikTok, Meta or Google ads | Creative library, original angles and measurable test brief |
| Improve website SEO | Query/intent map, verified technical issues and content priorities |
| Prepare screenshots and metadata | Genuine UI capture plan, truthful copy and asset checklist |
| Check launch readiness | Evidence of what passes and exact outstanding device/store gates |

Research, design, development, QA, release and growth are independent entry points. The assistant should produce a useful first result without forcing the whole agency process.

## A good first response

The assistant states the outcome it understands, the next concrete action and any meaningful assumption. It gathers context from available files before asking for it again. If one missing choice blocks the work, it asks one short question with sensible choices and continues independent preparation. It keeps technical setup details secondary unless they help you resolve a real blocker.

At completion you receive the result, what changed, how it was checked and any remaining decision. Source changes, device evidence, deployments, paid runs and store approval are reported separately. Publication, outreach, payments, account changes and submissions follow your actual authorized scope.
